# Review of 381b90e

## Implemented: read-only relock reference

The previous Lock Wizard generated executable batches containing `erase efisp`
or `oem lock` without verifying firmware authenticity, rollback compatibility,
device identity or the applicable procedure. Its standard path also listed
xiaomi.eu as a source of stock firmware. Selecting an unlock-method radio button
cannot establish that relocking is safe.

The wizard now shows a reference in English, Russian and Azerbaijani. It does not
query USB, generate command files or offer a lock action. The device profile is
not treated as evidence of a safe relock. This intentionally removes batch
generation; it does not implement a different recovery technique.

Validation: `python -m unittest discover -s tests -v`. The offline tests cover all
loaded profiles, an unknown device and all three languages. They exercise every
button with process execution and file writes blocked. No phone operations or
visual GUI testing were performed for this patch.

General platform reference (not a pandora-specific recipe):
https://source.android.com/docs/core/architecture/bootloader/locking_unlocking

## Outstanding findings — not fixed in this patch

1. **Support bundle exposes private data.** `_do_support_bundle` recursively
   includes all reports, including snapshot ZIPs, tokens and binary dumps, then
   suggests attaching the bundle to GitHub. Implement an explicit allowlist and
   reviewed redacted export. Do not publish existing bundles without review.
2. **Firmware comparison is overstated.** `_do_compare` locates an OTA but does
   not read its manifest or compare image hashes. It compares partition sizes
   against profile constants. Matching sizes cannot establish GPT integrity,
   authenticity or readiness to lock; mismatches do not alone prove corruption.
3. **UFS benchmark is not a solder-health diagnosis.** Cached reads, workload,
   temperature and free space confound speed. The implementation writes 2.5 GiB,
   uses fixed temporary names and keys baselines by codename rather than physical
   device. It needs exclusive temporary files, free-space and return-code checks,
   cleanup on failure, and neutral benchmark wording before broader use.
4. **Device selection is not pinned.** adb/fastboot calls lack an explicit serial;
   background monitoring can overlap commands. A selected GUI profile does not
   bind subsequent commands to that physical phone. Unknown profiles must not
   default to a pandora/exploit recovery procedure.
5. **Evidence and history need separation.** The existing lessons claim an atomic
   MiFlash relock operation, definite exploit residues, guaranteed certification
   and precise lifespan loss after repair without supporting measurements or
   implementation evidence. Preserve the owner's repair account, but label it
   as reported experience. The retained pre-repair log establishes unbootable
   slots, not the full cause of the failure. The description also labels an
   OS4 version as HyperOS 3; verify the actual post-repair version with the owner.
6. **Loader compatibility is not proven by UFS vendor.** `UFS_MANUFACTURERS`
   gives auth-free compatibility verdicts from a storage-name prefix alone.
   Those verdicts require evidence for the exact device, loader and firmware.

Scope: focused source review, not an exhaustive security audit. Legacy utilities
and all remaining device operations have not been certified safe by this review.
